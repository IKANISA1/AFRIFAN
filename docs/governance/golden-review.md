# Golden Baseline Review Policy

This file governs current AFRICLUB visual baselines. It is not a historical
evidence archive.

## Scope

Golden images may cover only the football-platform boundary defined in
`docs/blueprint.md`: supporter home, club, fixtures, results, standings,
predictions, membership, contributions, tickets, shop,
settings, role-gated internal mobile administration, and shared design primitives.
Internal admin workflows keep their role boundary and operational confirmation
contracts; their visual comparison uses shared component patterns.

Every baseline listed in `docs/governance/golden-baselines.json` must:

- be generated by a tracked test;
- use synthetic, non-production data;
- include an exact SHA-256 digest;
- identify viewport, pixel ratio, theme, locale, runtime, app version, and
  build number;
- contain no supporter identity, contact, payment, ticket, membership, or
  operator secret;
- match the current repository boundary and design authority.

## Review Procedure

1. Start from a clean, identified checkout.
2. Run the focused golden test without updating baselines.
3. Treat any pixel difference as a failure until reviewed.
4. Confirm the changed state is intentional, accessible, privacy-safe, and
   consistent with the selected `revolut-design` skill. Repository design files
   record product mappings and evidence; they do not override that authority.
5. If accepted, regenerate only the affected baseline with
   `flutter test --update-goldens <test-file>`.
6. Run the focused test again without `--update-goldens`.
7. Recalculate the digest in `golden-baselines.json`.
8. Run `tools/scripts/validate_golden_contract.sh` and the evidence privacy
   validator.

Never regenerate all baselines to hide an unexplained change. Never copy an
image from an output directory into a golden folder without an executable test
that reproduces it.

## Required State Coverage

Critical journeys cover the applicable subset of:

- loading, content, empty, error, offline, retry, and permission states;
- enabled, disabled, selected, focused, pressed, success, warning, and
  destructive states;
- compact phone, standard phone, large phone, tablet, landscape, and keyboard
  layouts;
- light, dark, high-contrast, 200-percent text, and reduced-motion modes.

Unavailable states are recorded as not applicable with a reason. They are not
silently omitted.

## Acceptance Rules

A baseline is accepted only when:

- the rendered hierarchy preserves football workflows and follows the selected
  skill's visual typology;
- touch targets, focus order, text scaling, contrast, semantics, and safe-area
  handling pass;
- loading and recovery preserve layout stability;
- image-rights and privacy controls fail closed;
- the test and manifest point to the same file and dimensions;
- the manifest digest matches the tracked file exactly.

Local golden acceptance does not prove physical-device accessibility,
production data behavior, store approval, deployment, or accountable release
authorization.
